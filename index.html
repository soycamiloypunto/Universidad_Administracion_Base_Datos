Momento 2: Diagnóstico DBA e Impacto en el Negocio (1.0 min)

1. Brecha de Seguridad

Uso generalizado de la cuenta root compartida entre desarrolladores y operarios. Ausencia de roles y mínimo privilegio.

Impacto: Riesgo inminente de borrado accidental y fuga de datos personales (Habeas Data).

2. Falta de Auditoría

Sin registro de quién modifica estados de pago o totales de pedidos. Discrepancias financieras sin trazabilidad forense.

Impacto: Desconfianza de compradores y descontrol contable con el campesinado.

3. Lentitud y Sin Backups

Consultas de despacho con Full Table Scan sobre +5.000 pedidos. Sin política de respaldo ni plan de recuperación ante desastres.

Impacto: Cuellos de botella en ventas y riesgo de quiebra total por pérdida de datos.

Pregunta Central del Proyecto

¿Cómo puede un DBA diseñar una estrategia pequeña y realista que garantice disponibilidad, seguridad, mantenimiento y rendimiento en un escenario real?

Momentos 3 y 4: Propuesta DBA y Gestión de Recursos (2.0 min)

Componentes de la Estrategia

  • Almacenamiento: General Tablespace dedicado en InnoDB.
  • Seguridad: RBAC (Roles) y pruebas de GRANT / REVOKE.
  • Auditoría: Tabla inmutable y Triggers automáticos.
  • Automatización: SP y Event Scheduler para mantenimiento.
  • Optimización: Índices B-Tree analizados con EXPLAIN.
  • Respaldo: mysqldump consistente y simulación de fallo.

Gestión Física: Tablespace Dedicado

Aislamiento físico para evitar la saturación de ibdata1 y facilitar copias por datafile:

CREATE TABLESPACE ts_agrosilvania
  ADD DATAFILE 'ts_agrosilvania.ibd'
  ENGINE = InnoDB;

-- Tablas asociadas directamente al Tablespace:
CREATE TABLE pedidos (...) TABLESPACE ts_agrosilvania;

Momento 5: Automatización y Mantenimiento Periódico (1.0 min)

Stored Procedure: sp_mantenimiento_semanal_agro

  • ANALYZE TABLE sobre tablas de pedidos y productos para actualizar la distribución de claves en el optimizador InnoDB.
  • OPTIMIZE TABLE sobre la tabla de auditoría para desfragmentar espacio libre en disco.
  • Detección y conteo de pedidos cancelados antiguos (>180 días).
  • Registro de tiempo en milisegundos en la bitácora log_mantenimiento_dba.

Programación Desatendida con Event Scheduler

Ejecución automática sin necesidad de intervención manual:

SET GLOBAL event_scheduler = ON;

CREATE EVENT evt_mantenimiento_semanal_agrosilvania
ON SCHEDULE EVERY 1 WEEK
STARTS '2026-11-01 02:00:00'
DO
  CALL sp_mantenimiento_semanal_agro();

Momento 6: Seguridad RBAC y Disparadores de Auditoría (1.0 min)

Control de Acceso Basado en Roles (RBAC)

  • rol_app_backend: Permisos DML (SELECT, INSERT, UPDATE, DELETE). Sin DDL.
  • rol_auditor_seguridad: Solo lectura (SELECT).
  • rol_operador_bodega: UPDATE solo sobre estado_pedido.
  • Evidencia GRANT / REVOKE: Demostración de asignación de privilegios temporales y su revocación inmediata verificada con SHOW GRANTS.

Trigger de Auditoría: trg_audit_pedidos_update

Captura forense ante cualquier mutación de estado o monto:

CREATE TRIGGER trg_audit_pedidos_update
AFTER UPDATE ON pedidos FOR EACH ROW
BEGIN
  IF (OLD.estado_pedido <> NEW.estado_pedido) THEN
    INSERT INTO auditoria_pedidos (
      id_pedido, tipo_accion, estado_anterior,
      estado_nuevo, usuario_modificador, fecha_modificacion
    ) VALUES (
      OLD.id_pedido, 'UPDATE', OLD.estado_pedido,
      NEW.estado_pedido, USER(), NOW()
    );
  END IF;
END;

Momento 7: Respaldo y Simulación de Recuperación (1.0 min)

1. Política de Respaldo Consistente en Caliente

Uso de --single-transaction para garantizar consistencia transaccional MVCC sin bloquear las ventas campesinas:

docker exec mysql-agrosilvania-db mysqldump \
  -u dba_admin -pDbaPassword2026! \
  --single-transaction --quick --routines --triggers \
  --databases agrosilvania_db > backup_full.sql

2. Simulación de Falla y Restauración

  • Falla provocada: Borrado accidental de tabla transaccional: DROP TABLE detalle_pedidos;.
  • Desastre comprobado: La aplicación falla con error 1146 (Tabla no existe).
  • Recuperación demostrada: Restauración por volcado SQL en menos de 30 segundos.
  • Validación: Integridad referencial comprobada al 100%.

Momento 8: Optimización con EXPLAIN ANALYZE (1.5 min)

Antes: Sin Índice B-Tree

Consulta sobre +5.000 pedidos entregados en últimos 90 días:

-> Filter: ((p.estado_pedido = 'ENTREGADO') and ...)
    -> Table scan on p (cost=520.25 rows=5000)
        Time: 14.8 ms (Escaneo Completo)

Tipo de acceso: ALL (Full Table Scan)

Después: Con Índice Compuesto

CREATE INDEX idx_pedidos_estado_fecha
ON pedidos (estado_pedido, fecha_pedido);

-> Index range scan on p using idx_pedidos_estado_fecha
    (cost=42.10 rows=410)
    Time: 0.8 ms (Reducción del 85% de CPU)

Tipo de acceso: range / ref (Selectividad Óptima)
